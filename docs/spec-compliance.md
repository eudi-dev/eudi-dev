# Spec compliance

This page lists which specifications of the EUDI Architecture and Reference Framework the wallet supports. The wallet reports unsupported mechanisms when it encounters them ([ADR-0013](adr/0013-only-the-eudi-stack-is-supported.md)).

The [EUDI version table and test certificate profiles](test-certificates.md) list the versions, checked on 1 October 2026.

Three settings control validation:

- `--mode strict` rejects validation violations. `--mode debug` reports them and continues where the flow can proceed. Advisory findings are warnings in both modes. Each finding cites the specification and rule.
- `--haip` enables the HAIP 1.0 profile checks listed below.
- `--arf` enables the ARF checks of access certificates, registration certificates and received credentials (see [ARF checks](wallet/presenting.md#arf-checks)).

`--vci-version 1.0` (default) uses the published OpenID4VCI version. `1.1` adds draft features when the issuer advertises them. See [OpenID4VCI feature level](wallet/issuing.md#openid4vci-feature-level).

## OID4VP 1.0 (OpenID for Verifiable Presentations)

| Feature | Status | Notes |
|---------|--------|-------|
| Authorization request parsing | Implemented | `openid4vp://`, `haip-vp://`, `eudi-openid4vp://`, `eu-eaap://` schemes |
| Request Object parameter extraction | Enforced | The wallet uses only the Request Object parameters (§5.10.1: "The Wallet MUST only use the parameters in this Request Object, even if the same parameter was provided in an Authorization Request query parameter"). A parameter missing from the Request Object counts as absent. A Request Object `client_id` that differs from the outer one aborts the flow |
| Undefined parameters | Warned | The wallet warns in every mode about request parameters that OID4VP 1.0 does not define and about response fields other than `redirect_uri` (§8.2). RFC 6749 §3.1 requires ignoring unrecognized parameters |
| Required request parameters | Enforced | `nonce` (§5.2), exactly one of `dcql_query` and `scope` on a `vp_token` request (§5.1), `state` when a credential query sets `require_cryptographic_holder_binding` to `false` outside the Digital Credentials API (§5.3), and no `redirect_uri` alongside `response_uri` (§8.2). The wallet defines no `scope` values (§5.5), so it answers a request with only `scope` with `invalid_scope` (§8.5) |
| `request_uri` (GET) | Implemented | Fetches and parses signed request objects |
| `request_uri_method=post` | Implemented | Sends `wallet_metadata` and `wallet_nonce`. The request object must contain the `wallet_nonce` sent by the wallet (§5.10.1). A missing or different value is a finding. Strict mode refuses it |
| Encrypted request objects (JWE) | Implemented | The wallet always sends an encryption key in `wallet_metadata` and decrypts an encrypted request object. `--require-encrypted-request` rejects an unencrypted one |
| DCQL query evaluation | Implemented | Includes `credential_sets` constraints. The wallet checks the query against §6. Each credential query needs `id`, `format` and `meta`. Each claim needs a non-empty `path`, and claim ids are unique. `claim_sets` needs `claims` and references only their ids. `trusted_authorities` entries need a `type` and non-empty `values`. `credential_sets` options are non-empty and reference only credential query ids. Strict mode refuses a query that breaks these rules with `invalid_request`. Debug mode warns and evaluates the query as far as it can. If an otherwise matching credential lacks some required claim paths, debug mode warns and continues. Strict mode treats that credential as non-matching |
| `require_cryptographic_holder_binding` | Implemented | The parameter defaults to `true` (§6.1). An SD-JWT VC without `cnf`, an mdoc without a device key and a `jwt_vc_json` credential (presented without a Verifiable Presentation, Appendix B.1) only match a query that sets it to `false`. In strict mode an mdoc without a device key matches no query. A value other than `true` or `false` is a warning in debug mode and refused in strict mode. For a query that requires holder binding, debug mode still matches an unbound credential and flags it in the consent dialog. Strict mode lists it among the non-matching credentials, and you can still pick it |
| `vct_values` matching across extending types | Implemented | A credential matches a `vct_values` entry for its own type, for a type in its `aka_vcts` claim, or for a parent type. So any domestic PID (`urn:eudi:pid:de:1`, `urn:eudi:pid:fr:1`, …) matches a request for `urn:eudi:pid:1`. ARF Annex 2 PID_14 defines these domestic PID types. Matching goes in that direction only. A match does not establish trust (see [credential type inheritance](wallet.md#credential-type-inheritance)) |
| `multiple` | Implemented | Without `multiple`, the wallet sends the newest matching credential. With `multiple: true` it sends all matching credentials. A batch counts as one credential. A `multiple` value other than `true` or `false` produces a warning. Strict mode refuses the query (§6.1) |
| `direct_post` response mode | Implemented | |
| `direct_post.jwt` response mode | Implemented | The response is an unsigned, encrypted JWT (§8.3). A request without a usable encryption key in `client_metadata.jwks`, or without a supported `enc`, is refused with `invalid_request` before the consent dialog. This applies to every encrypted response mode. The verifier gets no error response, because the wallet could not encrypt that either |
| `dc_api` response mode | Implemented | Browser API responses via `/api/dc-api` |
| `dc_api.jwt` response mode | Implemented | Encrypted Browser API responses via `/api/dc-api` |
| Response encryption key | Implemented | The response JWE is encrypted to the Verifier's `client_metadata.jwks` key. ECDH-ES for an EC P-256 key (the OID4VP baseline, preferred when the Verifier offers both) or RSA-OAEP for an RSA key. If the Verifier publishes only a key marked for signing, debug mode warns and encrypts to it anyway. Strict mode refuses the request. Under `--haip`, only ECDH-ES on P-256 is conformant (§5). Any other key is a violation |
| JAR (signed request objects) | Implemented | The JWS signature is verified with the leaf `x5c` key in every mode. Strict mode rejects an invalid signature. Debug mode reports it and continues. Every `x5c` certificate must be within its validity period (RFC 5280 §6.1.3 (a)(2)), also a lone signer certificate. The chain is checked for internal consistency. It is not anchored to a pre-registered verifier CA (see [SECURITY.md](../SECURITY.md)). With `--arf` the wallet checks the chain against the CAs on its `access-ca` lists |
| `x509_san_dns:` client_id | Implemented | Verified against the leaf certificate SAN |
| `x509_hash:` client_id | Implemented | SHA-256 of the leaf certificate matched against the prefix value |
| `redirect_uri:` client_id | Implemented | Requires unsigned request objects and checks that the prefix value matches `response_uri` |
| `verifier_attestation:` client_id | Validated | Checks the attestation `typ`, `sub`, `exp` and `cnf` claims. Verifies the Request Object with the `cnf` key and the attestation with its `x5c` certificate. The wallet has no trust anchors for attestation issuers, so it reports the signer as not verified |
| `decentralized_identifier:` client_id | Validated | Validates the DID format and cross-checks `kid`. DID resolution is not implemented, so the wallet reports the Request Object signature as not verified ([ADR-0013](adr/0013-only-the-eudi-stack-is-supported.md)) |
| Pre-registered client (no prefix) | Validated | A Client Identifier without a `:` refers to a pre-registered client (§5.9.2). The wallet does not report it as an unknown prefix. No client keys are pre-registered with this wallet, so it reports the Request Object signature as not verified |
| `origin:` client_id | Refused | §5.9.3 reserves the prefix: "The Wallet MUST NOT accept this Client Identifier Prefix in requests". The prefix identifies the audience of a Digital Credentials API presentation. The wallet derives that audience from the caller origin reported by the platform |
| `openid_federation:` client_id | Refused | §5.9.3 defers the prefix to OpenID Federation. Trust chain resolution is not implemented, so the request is refused |
| Unsigned Digital Credentials API requests | Implemented | Per Appendix A.2, such a request carries no `client_id`. The wallet discards both `client_id` and `expected_origins` before processing it. The platform reports the caller origin. The presentation audience is that origin prefixed with `origin:` |
| `expected_origins` on signed Digital Credentials API requests | Enforced | Appendix A.2 requires the parameter on a signed request. The wallet returns an error when the caller origin is not among its entries |
| VP Token as a JSON object | Implemented | One entry per credential query id, each with an array of presentations (§8.1). Multiple credentials go in a single response |
| `fragment` response mode | Implemented | Builds the redirect URL with `vp_token` and `state` as fragment parameters. Not the default |
| SIOPv2 self-issued `id_token` | Implemented | `response_type=vp_token id_token` or `id_token` alone |
| Request object `typ` header | Enforced in strict mode, with one deliberate deviation | A signed Request Object needs the `typ` `oauth-authz-req+jwt`. Strict mode refuses a missing or different one, and debug mode logs a warning and continues. An unsigned Request Object (`alg` `none`) without `typ` only gets a warning, also in strict mode. §5 says "Wallets MUST NOT process Request Objects where the typ Header Parameter is not present". The wallet deviates because the OIDF conformance suite (release-v5.3.2) sends its unsigned `request_uri` objects without `typ`. An unsigned object also has no signature for `typ` to protect |
| Request object `exp` and `aud` | Enforced in strict mode | A Request Object whose `exp` has passed is a finding, with one minute of clock skew (RFC 7519 §4.1.4). Its `aud` must be `https://self-issued.me/v2` (§5.8). The wallet publishes no metadata with an issuer, so no Verifier can discover it dynamically. Strict mode refuses either finding, and debug mode logs a warning and continues. A signed Request Object without `aud` only gets a warning (RFC 9101 §4). A Digital Credentials API request without `aud` gets none, as in the example of Appendix A.3.2.1. The presentation request of Interactive Authorization (OpenID4VCI 1.1 §6.2.1.1) has no `aud` rule |
| `trusted_authorities` (`etsi_tl`, `aki`) | Implemented | Filters credentials by checking the issuer certificate chain against ETSI trusted lists or by matching Authority Key Identifier values |
| `transaction_data` | Enforced in strict mode | §5 requires a wallet that does not support the parameter to reject a request carrying it. Strict mode rejects it. Debug mode logs a warning and continues |
| `verifier_info` | Implemented | The wallet shows the purpose from a wallet-relying-party registration certificate (typ `rc-wrp+jwt` per ETSI TS 119 475, format `registration_cert` per ETSI TS 119 472-2) (§5.1). The data is the base64url encoding of the compact JWT (ETSI TS 119 472-2 V1.3.1 RO-16). The wallet also reads the plain compact JWT used in `issuer_info` (ETSI TS 119 472-3 V1.1.1 ISS-MDATA-REG_CERT-4.2.3-06). The certificate's signature is checked against its own x5c leaf. A registration certificate counts only if it belongs to the access certificate that signed the request object. A request without a request object shows no purpose. The consent dialog also links the registered privacy policy (ARF RPA_10). Other attestation formats are ignored. `--arf` checks the certificate against the ARF (see [ARF checks](wallet/presenting.md#arf-checks)) |
| ARF relying party checks (`--arf`) | Enforced in strict mode | Checks the access certificate (RPA_03, RPA_04) and the registration certificate (RPRC_02a, RPRC_17, RPRC_17a). The request may carry at most one registration certificate (RPRC_19). A request without one gets a warning in every mode, because wallets must check registration certificates only from 11 August 2028 (CIR (EU) 2026/1731). The wallet checks the registrar's status list for a revocation. The list must chain to a trusted registrar (RPACANot_03b). The wallet also checks whether the request asks for more than was registered (RPRC_21) and whether the response mode encrypts the presentation (OIA_09). Strict mode refuses a request with a finding. If a trusted access certificate signed the request and its client identifier is valid, the wallet sends the verifier the error (§8.5, RFC 6749 §4.1.2.1): `access_denied` when only ARF findings remain, otherwise the §8.5 code of the request error. This also works over the Digital Credentials API and from `wallet accept`. Debug mode warns and returns the findings in the API response. Without `--arf` the wallet does not check them. See [ARF checks](wallet/presenting.md#arf-checks) |
| ARF issuer checks (`--arf`) | Enforced in strict mode | Before it requests a credential, the wallet checks the issuer. The metadata must be signed with an access certificate (ISSU_22, ISSU_32) from a trusted access certificate authority (ISSU_24, ISSU_34). A registration certificate in `issuer_info` (ETSI TS 119 472-3 V1.1.1 §4.2.3) must come from a trusted registrar (ISSU_23c, ISSU_33a). It must be valid and not revoked (RPRC_22a). It must identify the access certificate's provider (RPRC_22b), have the provider entitlement for the offered type (ISSU_24a, ISSU_34a) and list that type (RPRC_23, ISSU_24b, ISSU_34b). Metadata without a registration certificate gets a warning in every mode, because wallets must check one only from 11 August 2028 (CIR (EU) 2026/1731). Strict mode refuses the offer before the consent dialog. Debug mode warns and returns the findings in the issuance result. A received credential must chain to the trusted list of its catalogue entry, or for a PID or a PuB-EAA to a list of its type on the list of trusted lists (ISSU_07 to ISSU_10). A PID, QEAA or PuB-EAA entry must link a readable trusted list. ISSU_10 applies only when the wallet has anchors. A fetched trusted list must be signed by the wallet CA or a `--trusted-list-ca` CA (PPNot_05, TLPub_05, TLPub_07). The received credential must be of the requested type (ISSU_06), the copies of a batch must share one validity period (ISSU_11a), and the credential must not be expired, not yet valid or revoked (CIR (EU) 2024/2982 Article 4(3)(d)). An unreadable status list is a finding. If a check fails, strict mode doesn't store the credential (ISSU_11b). Manual import skips these checks. An offered type outside the catalogue only gets a warning. See [issuing](wallet/issuing.md#arf-checks) |
| Relying party registrar | Implemented | The wallet registers verifiers and issuers in the TS05 v1.5 data model and serves the TS05 registry API. It issues access certificates (ETSI TS 119 411-8) for CSRs and registration certificates (ETSI TS 119 475) per intended use (RPRC_09) or per issuer service (RPRC_13). The registrar returns a verifier's certificate in a `verifier_info` value (ETSI TS 119 472-2 RO-13 as adapted by CIR (EU) 2026/1731 Annex XII), and an issuer's certificate in an `issuer_info` value (ETSI TS 119 472-3 V1.1.1 ISS-MDATA-REG_CERT-4.2.3-04 as adapted by Annex XI). Each array has only the `registration_cert` element. The wallet ignores other elements, such as a `registrar_dataset`. See [registrar](wallet/registrar.md) |
| Catalogue of attestations | Implemented | The registrar keeps a catalogue in the EC TS11 v1.0 data model (§4.3) and serves its API (§5.3): signed `GET /schemas` with filters and paging, `GET`, `PUT` and `DELETE /schemas/{schemaId}`. The schema behind a `dc+sd-jwt` schema URI is SD-JWT VC Type Metadata. The one behind an `mso_mdoc` schema URI lists the doctype's namespaces and elements, and has not been checked against ISO 23220-2. See [attestation catalogue](wallet/registrar.md#attestation-catalogue) |

HAIP §7 requires issuers to support ES256 |
| Key attestation proof types | Implemented | The key attestation (Appendix D) goes in the `key_attestation` header of a `jwt` proof (F.1). Under the `attestation` proof type it is the proof itself, with the issuer's `c_nonce` inside the attestation (F.3). The wallet picks `attestation` when it is the only type in `proof_types_supported` or when the `jwt` type requires a key attestation. Otherwise it picks `jwt` |
| Demo issuer key proofs | Implemented | The demo issuer offers the `jwt` and `attestation` proof types with ES256, ES384 and ES512 (CIR (EU) 2024/2979 Annex Ib SA-3 and TR_KA-4). It verifies a key attestation and checks that a jwt proof is signed by the first attested key (TR_KA-5, TR_KA-6). It binds one credential to each attested key (ETSI TS 119 472-3 CRED-REQ-PROC-4.6.2.1-04). The jwt proof type requires a key attestation only with `--demo-issuer-key-attestation required`. See [the demo issuer](public-demo.md#demo-issuer-as-an-authorization-server) |
| Demo issuer credential encryption | Implemented | The demo issuer decrypts encrypted credential and deferred credential requests and encrypts the response when asked (§10). Error responses stay plain (§8.3.1.2) |
| Deferred credential issuance | Implemented | Both grant flows poll `deferred_credential_endpoint` with the `transaction_id`. A credential response that carries both `credentials` and `transaction_id` breaks §8.3. Strict mode refuses it. Debug mode warns and stores the credentials |

Any 2xx is a success (§11.2). The wallet reports error responses that match neither of the two defined in §11.3 |
| Transaction code | Implemented | The wallet sends a `tx_code` when the offer's pre-authorized grant requires one (§4.1.1). `wallet accept` prompts for it at the terminal when it runs the flow itself. Without a code, the wallet refuses the issuance before it uses the pre-authorized code. The error states the length and input mode required by the offer |

| Credential Issuer Metadata retrieval | Implemented | `Accept: application/json, application/jwt` (§12.2.2). The response is refused unless `credential_issuer` is identical to the requested identifier (§12.2.4) |
| Signed Credential Issuer Metadata verification | Implemented | The wallet checks `typ`, an asymmetric `alg`, a `sub` matching the issuer identifier and the signature against the `x5c` leaf. | Registrar-style issuer authorization data | Implemented | The wallet serves the TS05 v1.5 registry API at `/api/registrar/wrp`. ## OID4VCI 1.1 draft (selected with `--vci-version 1.1`)

These features are active only with `--vci-version 1.1` and only when the issuer's metadata advertises them.

1.1 is an editor's draft. The wallet implements the revision of 4 August 2026 and `draft-ietf-oauth-first-party-apps-04` (profiled by §6).

| Feature | Status | Notes |
|---------|--------|-------|
| Interactive Authorization (§6) | Implemented | Used when the authorization server publishes `authorization_challenge_endpoint` (§13.3). It replaces the redirect flow of §5 and needs no `--vci-redirect-uri`. At feature level 1.0, the activity log shows the flag that enables it |
| Authorization Challenge Request (§6.1) | Implemented | The initial request carries `interaction_types_supported`, PKCE S256, the credential scope or `authorization_details` and the offer's `issuer_state`. Later requests carry the latest `auth_session`. A presentation interaction must carry one (§6.2.1.1). For `auth_via_web` the wallet ignores it (§6.2.1) and takes it from the redirect back. The request after `auth_via_web` also carries the `code_verifier` (§6.2.1.2). The code arrives in `authorization_code`. The token request for it omits `redirect_uri` (first-party-apps §6). For a code from the auth_via_web browser redirect, the token request repeats the redirect URI, as RFC 6749 §4.1.3 requires |
| Presentation interaction (§6.2.1.1) | Implemented | The wallet advertises only interactions that it can complete (§6.2.1). The wallet accepts a signed or unsigned `openid4vp_request`. `response_mode` must be `ia_post` or `ia_post.jwt`. The wallet sends the response as `openid4vp_response` in the next challenge request. If no credential matches, it answers with an OpenID4VP error |
| Presentation binding, SD-JWT VC (Appendix A.3.5) | Implemented, with a caveat | The Key Binding JWT `aud` is the Authorization Challenge Endpoint prefixed with `ia:`. Only A.3.5 says "the derived **Origin** ... of the Authorization Challenge Endpoint". A.1.1.5 (JWT VC), A.1.2.5 (Data Integrity) and A.2.5 (mdoc) bind the endpoint itself. §6.2.1.5 describes "binding the Authorization Challenge Endpoint to the Verifiable Presentation". A.3.5's own example also uses the endpoint. So the wallet sends the endpoint. A verifier that reads A.3.5 literally computes `ia:https://host` and refuses the presentation |
| Presentation binding, mdoc (Appendix A.2.5) | Implemented | `OpenID4VCIIAEHandover` over the challenge endpoint, the nonce and (for `ia_post.jwt` only) the encryption key thumbprint. Checked against the worked example in the appendix |
| `expected_origins` check (§6.2.1.1, §6.2.1.5) | Enforced | When present, it must contain only the derived origin of the challenge endpoint, compared exactly. This detects a request forwarded from another authorization server. Unsigned requests are checked too, because no platform reports the caller origin here. Strict mode refuses any other value. Debug mode warns and continues |
| `auth_session` beyond one issuance | Deliberate deviation | Section 5.3.1 of the first-party-apps specification says a client "MUST store the auth_session beyond the issuance of the authorization code to be able to use it in future requests". The wallet keeps it for one exchange only. A stored session would let an authorization server correlate later issuances. Dropping it costs at most one more interaction |
| The `presentation_during_issuance_session` extension | Not implemented | A community extension outside the OpenID4VCI drafts. The challenge endpoint responds with HTTP 400 and a `presentation` member that carries an `openid4vp://` request URI, without `interaction_type_required`. The extension expects the presentation at the verifier's own `response_uri`. These response fields distinguish it from the §6 flow. The wallet aborts and reports the missing member (§6.2.1) |
| Authorization via web (§6.2.1.2) | Implemented | The wallet advertises `urn:openid:dcp:ia:auth_via_web` when an https redirect URI is configured and the server publishes an `authorization_endpoint`. It turns the response's `request_uri` into an authorization request (RFC 9126 §4) and passes the sign-in URL to the user's browser. The redirect back carries either a `code` or an `auth_session` that continues the challenge exchange. The token request repeats the redirect URI for a code obtained this way (RFC 6749 §4.1.3) and omits it for one from the challenge endpoint (first-party-apps §6). If the server requests an interaction type that is not advertised, the wallet refuses it |
| Custom interaction types (§6.2.1.3) | Not implemented | An unsupported `interaction_type_required` aborts the issuance (§6.2.1) |

## HAIP 1.0 (High Assurance Interoperability Profile)

`--haip` enables the checks below. Strict mode rejects violations. Debug mode logs them and continues. If a verifier offers only one supported AES content encryption algorithm, the wallet issues an advisory in either mode.

| Feature | Status | Notes |
|---------|--------|-------|
| VP `response_type` | Enforced | §5: "The Response type MUST be vp_token" |
| VP response modes | Enforced | Only `direct_post.jwt` (§5.1) and `dc_api.jwt` (§5.2) |
| VP Client Identifier Prefix | Enforced | §5 requires `x509_hash` for signed requests, so `x509_san_dns:` is a finding |
| VP request signature | Enforced | The Request Object signature is verified, and the `x509_hash` value must be the SHA-256 of the certificate that signed it |
| VP signing certificate rules | Enforced | §5: the certificate signing the request must not be self-signed, and the trust anchor must not be in the `x5c` header |
| VP signed request object (JAR) | Enforced | §5.1 requires JAR with the `request_uri` parameter, so an inline request object over redirects is refused. Unsigned requests are accepted only over the Digital Credentials API, where §5.2 requires them and they carry no `client_id` |
| VP DCQL query | Enforced | §5: "The DCQL query and response MUST be used as defined in Section 6 of [OIDF.OID4VP]" |
| VP credential formats | Not restricted | §5.3.1 and §5.3.2 apply when an mdoc or an SD-JWT VC is used. A query for another format is outside the profile and is not refused |
| VP Verifier response encryption metadata | Advisory | §5 requires both `A128GCM` and `A256GCM`. If the Verifier offers only one and the wallet can use it, the wallet warns in either mode |
| VP `expected_origins` | Enforced | A signed Digital Credentials API request must list the caller origin (OpenID4VP Appendix A.2, incorporated by §5.2) |
| VP request object `alg` | Implemented | §7 requires wallets to support at least `ES256` for signed presentation requests. The wallet advertises it in `request_object_signing_alg_values_supported` and verifies the other ES, RS and PS algorithms too |
| DPoP proof shape | Implemented | `htm` and `htu` per RFC 9449 §4.2. `htu` is the target URI "without query and fragment parts". A proof sent with an access token carries `ath` (the SHA-256 of the token). Each proof has a fresh `jti`. When the server asks for a `DPoP-Nonce`, the wallet echoes it and retries once |
| VCI authorization code profile requirements | Enforced | The client uses PAR, PKCE S256 and DPoP. An offer that uses the authorization endpoint is rejected unless the authorization server supports the authorization code flow and offers a pushed authorization request endpoint (or an `authorization_challenge_endpoint`, since interactive authorization sends no pushed request). It is also rejected when the server advertises PKCE without `S256`. The DPoP signing algorithms are open, because §7 does not list DPoP proofs among the uses that require `ES256`. Metadata that omits PKCE, DPoP and client authentication passes, because §4 defers those to FAPI 2.0. FAPI 2.0 constrains behaviour only. For a pre-authorized code offer, only the https rule of OpenID4VCI 1.0 §12.2.1 applies |
| VCI encrypted credential responses | Implemented | Requests `credential_response_encryption` and decrypts returned compact JWEs |
| VCI received credential | Enforced | §6.1.1: an SD-JWT VC carries the issuer's signing certificate and its chain in `x5c`, without the trust anchor, and the signing certificate is not self-signed. The wallet checks every received credential, on every issuance flow and for every copy of a batch |

The OIDF HAIP wallet conformance plans test these rules.

## SD-JWT (Selective Disclosure JWT)

Selective disclosure is RFC 9901. The credential profile on top of it is `draft-ietf-oauth-sd-jwt-vc-19`.

| Feature | Status | Notes |
|---------|--------|-------|
| Parsing (header, payload, disclosures) | Implemented | |
| RFC 9901 §7.1 verification and processing | Enforced | Parsing applies all of §7.1 and refuses a credential that violates any of its MUST-reject conditions (a disclosure named `_sd` or `...`, a disclosure whose claim name already exists at the level of its `_sd` key, a disclosure whose element count does not match the position of its digest, a digest that appears twice, a disclosure not referenced by any digest) |
| `_sd` claim resolution | Implemented | Recursive. `_sd` must hold an array of strings (§4.2.4.1) |
| Array disclosures | Implemented | A `{"...": digest}` element must carry that one key and nothing else (§4.2.4.2). An element whose digest has no disclosure is removed (§7.1 step 3.d) |
| `_sd_alg` handling | Implemented | Compared case-sensitively, defaults to `sha-256`, and refused in any object nested within the payload (§4.1.1) |
| Key Binding JWT | Implemented | Generated during presentation |
| Signature verification (ES256/384/512) | Implemented | |
| Signature verification (RS256/384/512, PS256/384/512) | Implemented | |
| SHA-256/384/512 disclosure digests | Implemented | |
| Disclosure digest integrity check | Implemented | Checks that each disclosure hash appears in an `_sd` array |
| `kid` header on generated SD-JWTs | Implemented | Deterministic RFC 7638 thumbprint of the signing key |
| X.509 trust-chain based issuer key publication | Implemented | Generated SD-JWTs carry the leaf and intermediate certificates in `x5c` and omit the root. Wallet trusted lists publish the service certificates and provider CAs |
| SD-JWT VC `typ` header | Implemented | Generated credentials carry `dc+sd-jwt`. A credential with `vc+sd-jwt` still decodes, but it fails the type check. `validate`, the web validator and the demo verifier reject it in both modes. The wallet stores it with a warning in debug mode and refuses it in strict mode |
| Credentials with no selectively disclosable claims | Implemented | `_sd` is omitted from the payload and the serialization ends in a single tilde (SD-JWT VC §2.2.2.5 and RFC 9901 §4) |
| Registered claims that cannot be selectively disclosed | Enforced | `iss`, `nbf`, `exp`, `cnf`, `vct`, `vct#integrity`, `aka_vcts` and `status` are embedded plainly in generated credentials (SD-JWT VC §2.2.2.3). `iat` is plain too, except in a PID. A PID discloses `iat` selectively, because CIR (EU) 2024/2977 Annex section 4.2 (as replaced by CIR (EU) 2026/1731) makes every claim of a PID selectively disclosable that SD-JWT VC allows (ARF PID_21) |
| `nbf` on generated credentials | Implemented | Every generated SD-JWT VC carries `nbf` (ETSI TS 119 472-1 V1.2.1 EAA-5.2.7.1-01, and CIR (EU) 2024/2977 Annex section 4.2 for a PID). Without a configured start it is the issuance time |
| `aka_vcts` claim | Implemented | Read when matching a credential against a requested type (§2.2.2.2). Written into issued credentials whose type extends another. Never treated as evidence of issuer authorization (§7.7) |
| Type Metadata `extends` | Not implemented | The relationship is resolved from PID_14 for PID types and from `aka_vcts` for any type. EUDI PID `vct` values are URNs, and §5.4 does not cover URNs. The ARF only asks a Scheme Provider to "consider defining" a Type Metadata Document (Annex 2, ARB_31) |
| JWT VC Issuer Metadata key resolution | Implemented | `/.well-known/jwt-vc-issuer` is inserted between the host and the path of `iss` (SD-JWT VC §4), so a tenant-scoped issuer resolves. The document must contain `issuer` identical to `iss` and either `jwks` or `jwks_uri`, never both (§4.2 and §4.3) |
